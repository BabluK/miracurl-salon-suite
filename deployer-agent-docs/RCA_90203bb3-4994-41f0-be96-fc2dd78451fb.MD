# RCA — miracurl-suite.com (hair-hub-system) — Attendance empty & Dashboard "This Month" revenue missing in PROD

## Verdict
**Not an infra / deploy / OOM / DB-loss problem. This is a source-code regression in branch-scoping filters** that is incompatible with the production tenant's existing data. The endpoints return **200 OK** with empty/zero payloads — the data is present and untouched.

## What was ruled OUT (evidence)
- **Deploy completed fully.** Active run `90203bb3-4994-41f0-be96-fc2dd78451fb` (redeploy, trigger user_deploy) status = success; image built & rolled out; promote done.
- **No OOM / crash-loop.** Both pods `Running`, `restart_count: 0`, no OOMKilled / CrashLoopBackOff. The only events are transient `503 startup-probe` failures during the ~30s boot window (normal). NOTE: tier is now **tier_1 = 2Gi memory limit** (pod spec confirms `memory: 2Gi`), so the old 512Mi OOM history is resolved — memory is NOT the issue here.
- **No 500s / no ImportError.** Prod logs show the exact endpoints returning **200**: `GET /api/attendance/today?date=2026-08-02&branch=__main__` → 200, `GET /api/reports/dashboard?branch=__main__` → 200, `/api/staff` → 200, `/api/tenants/current` → 200. The recent `requests`/`asyncio` imports in `routes/tenant_settings.py` are fine — app booted cleanly, no import errors. (`asyncio`+`requests` are already available; nothing missing.)
- **MongoDB intact.** DB `hair-hub-system-miracurl_db`, 86 collections. Data present: staff=11, attendance=29, invoices=41, tenants=3. August invoices exist (INV-202608-0023/0022/0018 dated 2026-08-02). No data loss, correct DB binding.

## Root cause
Two endpoints filter by an effective `branch` that resolves to the sentinel `"__main__"`, and the `__main__` path filters to records whose branch is **empty/null**:

1. `backend/routes/staff_portal.py:706` (`attendance_today`):
```python
staff_q = {"active": True}
if branch:
    staff_q["branch"] = {"$in": [None, ""]} if branch == "__main__" else branch
```
2. `backend/routes/reports.py:139-142` (`_branch_query`, used by `/reports/dashboard`):
```python
def _branch_query(branch):
    if branch == "__main__":
        return {"branch_name": {"$in": [None, ""]}}
    return {"branch_name": branch} if branch else {}
```

In production, this tenant's records DO NOT have empty branch, so `{$in:[None,""]}` matches **zero rows**. Verified counts for the owner's tenant `83ab97b6-b481-4172-afd7-53a46c93317d` (admin@miracurl.com):
- Active staff = **4 total**, with `branch ∈ [null,""]` = **0** → `attendance/today?branch=__main__` returns empty staff list → `total_staff:0`, empty roster → no performance board, no active staff, no check-in details, no rows.
- August invoices (not voided) = **15 total**, with `branch_name ∈ [null,""]` = **0** → dashboard `invoices_month = []` → `month_revenue = 0` → "This Month" KPI blank.

### Why "All branches" doesn't help & why it's empty for owner AND manager
- Frontend (`src/components/BranchSwitcher.jsx:77-78`): **"All branches" sends `branch=""`**, **"Main salon" sends `branch="__main__"`**. Every observed prod request went out as `branch=__main__`, i.e. the effective/selected branch is "Main salon only", not "All branches".
- `branch_lock()` (`backend/security.py:176`) forces a **manager**'s own locked branch; owners pass through. Either way the effective value lands on `__main__` for these users, hitting the empty-branch filter.

### Underlying data inconsistency (the reason `__main__` matches nothing)
The branch identifiers are not normalized across collections:
- Tenant `83ab97b6` configured branch **name** = `"Miracurl Unisex Family Salon- AECS"` (id `8dcbbe24…`).
- Staff docs carry `branch: "Miracurl Unisex Family Salon"` (no `- AECS` suffix) — doesn't match the tenant config.
- Recent invoices/attendance carry `branch_name: null` / no `branch` field at all (attendance docs have NO branch field).

So NO branch value ("__main__", the configured branch name, or "") lines up consistently across staff + invoices + attendance.

## Why PREVIEW works but PROD doesn't (same code)
Preview's tenant is a fresh single-salon setup where staff & invoices have **empty/null** branch, so the `__main__` → `{$in:[None,""]}` filter matches everything (that's the "9 staff / month_revenue present" they saw). Prod's tenant has real, un-normalized branch names on its records, so the same filter matches nothing. The difference is DATA, not code — which is exactly why it reproduces only in prod.

## Recommended fix (code-side — owned by app agent)
Decide the intended semantics of the branch filter and make it consistent with the data. Options, in order of preference:

1. **Treat `__main__` as "no branch constraint" (show all)** if that matches product intent for the main/owner view — i.e. don't add the `branch`/`branch_name` key when `branch == "__main__"`. This immediately restores attendance + month_revenue.
2. **Normalize branch data** so staff.`branch`, invoice.`branch_name`, and attendance branch all use the tenant's configured branch **name** (or better, a branch **id**), and backfill existing rows. Then filtering by a real branch works and `__main__` (unbranched) is only used when records are genuinely unbranched.
3. If `__main__` must mean "main salon only", ensure the default selected branch for owners/managers of a tenant that HAS branches is **"All branches" (`""`)**, not `__main__`, and make attendance/dashboard tolerate records whose branch is null by including them in the "all" view.

Files to change: `backend/routes/staff_portal.py` (~line 706, `attendance_today`), `backend/routes/reports.py` (~lines 139-142 `_branch_query` + `/reports/dashboard`), plus any other endpoint using the same `__main__ → {$in:[None,""]}` pattern (grep found similar handling in `staff_admin.py`, `appointments_pos.py`). Also reconcile the staff/invoice/tenant branch-naming mismatch.

## Note on verification
Root cause was verified directly against **live production data** via read-only mongo_query (counts above) plus reading the deployed run's source — stronger here than an eph reproduction, which is not possible because the fault requires the live prod DB (the eph sandbox has no app secrets/DB). No app state was mutated.
