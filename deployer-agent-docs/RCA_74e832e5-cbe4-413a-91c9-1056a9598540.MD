# RCA — "SMS: not configured" on POS receipts (hair-hub-system)

## Problem statement
POS billing receipts display "SMS: not configured". Reporter's premise: backend `sms_configured()` in `/app/backend/sms_service.py` returns False, and it returns True only when `MSG91_AUTHKEY` is set. Request: report presence/emptiness of MSG91 keys + SMS_PROVIDER in production, and whether logs contain sms/msg91 warnings/errors. Read-only.

## Scope
- Deployment: hair-hub-system (fdb90ac2…), active run `74e832e5-cbe4-413a-91c9-1056a9598540` (status: success, live, tier_1, cloudflare frontend).
- No changes made.

## Evidence — production secrets (list_secrets, ACTIVE run)
| Key | Present | Empty |
|---|---|---|
| MSG91_AUTHKEY | yes | **No (non-empty)** |
| MSG91_SENDER_ID | yes | empty (matches_expected=false vs preview `MIRACU`) — optional per reporter (falls back to DLT header "MIRACU") |
| MSG91_FLOW_ID | yes | empty (matches preview; optional — per-template IDs hard-coded) |
| MSG91_TPL_OTP | yes | non-empty |
| SMS_PROVIDER | yes | non-empty (set; value not disclosed by tooling) |

## Evidence — backend logs (last 1440 min, filter: sms|msg91|not configured|control.msg91)
- NO "not configured" warnings.
- NO MSG91 auth failures / 4xx from control.msg91.com.
- Present: repeated INFO `sms - INFO - HQ MSG91 template IDs applied from hq_settings`, and `GET /api/sms-packs → 200 OK` (many).

## Root cause
`MSG91_AUTHKEY` IS present and non-empty in production. By the stated logic of `sms_configured()` (True whenever `MSG91_AUTHKEY` is set), the production environment/secrets layer does NOT explain the "SMS: not configured" receipt line. There is no missing/empty required secret and no MSG91 error in logs. The reporter's premise (missing AUTHKEY → not configured) is not supported by the live run.

## What this means / remaining hypotheses (for E1)
Because the env var is correctly set, the "not configured" text on the receipt is driven by something other than the presence of `MSG91_AUTHKEY`. Candidates E1 should verify in source/runtime (cannot be confirmed from secrets/logs alone):
1. The receipt/POS code path may check a DIFFERENT gate than `sms_configured()` — e.g. a per-tenant/HQ `hq_settings` flag (note the recurring `HQ MSG91 template IDs applied from hq_settings` INFO suggests config is sourced per-tenant), or the value of `SMS_PROVIDER` not equalling the expected provider string ("msg91").
2. The stored `MSG91_AUTHKEY` value could be structurally present but invalid/placeholder — env metadata only proves non-empty, not validity. No msg91 4xx in logs, though, which weakly argues against active auth failures (SMS may simply not be attempted).
3. Frontend display / stale-bundle possibility on the receipt render.

## Notes / limitations
- Secret VALUES are never exposed; only presence/emptiness verified.
- MSG91_SENDER_ID empty in prod (preview=MIRACU) is optional and not the cause.
- No changes were made; deployment is healthy and live.
